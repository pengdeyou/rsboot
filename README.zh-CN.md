# rsboot

> ### 最快的 Rust Web 服务开发方式。
>
> 慢 I/O 负载下快于 axum 与 actix-web——200 并发 / 20 ms 延迟下 **9 687 QPS**，是自己旧同步实现的 **96 倍**。同时是上手最短的一条路：`Cargo.toml` 里一行依赖声明，信号处理、OpenAPI 文档、连接池全部内置，几行代码就能跑通端点。
>
> 但我们**不是裸吞吐冠军**，这份 README 也不装作是：无 I/O 的 JSON 路径上，高并发下 actix-web 领先约 18 %。下表把每一列都列出来，包括我们输掉的那几列。

扎根 Rust 生态的应用框架——FastAPI 式的声明式路由、类型化提取、自动 OpenAPI。**同步 handler 跑在栈式协程上，底层 socket 全程非阻塞**：慢 I/O 让出 worker，而不是把它占住。HTTP/1.1 协议栈、协程调度与事件循环全部自研——不引 tokio，不引 hyper，不引 axum。

[English](README.md) · [中文](README.zh-CN.md) · [Deutsch](README.de.md) · [Français](README.fr.md) · [العربية](README.ar.md) · [Русский](README.ru.md)

**状态：alpha（`0.1.0-alpha.1`）。** 核心链路——HTTP、路由、提取器、统一响应体、统一异常、OpenAPI、模块生命周期、优雅下线、协程调度、数据库 socket——已实现并有测试覆盖。SSE / WebSocket / JSON-RPC 尚未建设，见文末「已知限制」。

`rsboot` 是应用框架，[rsbatis](https://github.com/pengdeyou/rsbatis) 是 ORM。两者独立 crate、独立仓库、独立版本。

## 它要解决的问题

FastAPI 好用，靠的是三件事：声明式路由、类型即校验、文档自动生成。Rust 主流框架各缺一块：

| | handler 写法 | 代价 |
|---|---|---|
| axum / actix-web | `async fn` | `Send + 'static` 约束；不能跨 await 借 `&Request`；异步 DB/HTTP 会把 tokio + hyper + sqlx 一起拖进依赖树 |
| 纯同步框架 | `fn` | worker 数等于核数，吞吐上限是「worker 数 ÷ 阻塞时长」——一个慢依赖就能把整台服务卡死 |

第二行是实测出来的，不是推测：20 ms 下游延迟、200 并发，纯同步实现只有 **99 QPS**，两个 worker 全在等。

rsboot 把问题拆成两层：**连接层事件驱动，请求层跑有栈协程。** handler 保持普通同步签名，慢 I/O 时让出 worker 而不是占住它。

## 性能对比

与 axum、actix-web 同机对比。条件：4 核 Linux 虚拟机，三套服务**都是 2 个 worker 线程**，路由完全一致，三者同一时间窗口内逐一轮流压测，数字为 QPS。

| 场景 | rsboot | axum | actix-web |
|---|---:|---:|---:|
| `/slow` — 20 ms 延迟，5 并发 | **248** | 236 | 236 |
| `/slow` — 20 ms 延迟，20 并发 | **990** | 944 | 944 |
| `/slow` — 20 ms 延迟，200 并发 | **9 687** | 9 237 | 9 292 |
| `/json` — 4 并发，无阻塞 I/O | **160 006** | 130 504 | 140 917 |
| `/json` — 20 并发，无阻塞 I/O | **198 557** | 153 618 | 194 150 |

两行 `/json` 于 2026-11-26 重测；`/slow` 三行取自同一台机器的前一个窗口（协程路径此后未改动，但请当作另一次运行看，而不是同一份快照）。

这张表说明了什么，包括不替自己遮掩的部分：

- 存在阻塞的负载上，rsboot 三者中最快，但只比 axum/actix 高出几个百分点——因为三者都在「把 worker 占满」，收敛到同一量级。真正有价值的数字是**与自身旧实现的对比**：200 并发下 99 → 9 687 QPS，**96 倍**。协程层存在的全部理由就是这个。
- 纯 JSON 吞吐：当前窗口两档并发都由 rsboot 领先——4 并发比 actix 高 13.5 %、比 axum 高 22.6 %；20 并发比 actix 高 2.3 %、比 axum 高 29.2 %。但 20 并发那 2.3 % **落在噪声内**（这台 4 核机三轮跑了 193 k–210 k），所以那一行应当读成「与 actix 同档」，而不是「赢」。
- 这份 README 原先印过的两个数字都已**作废**。157 730：压测器自身每请求要花掉数微秒（这台测试机上一次 `Instant::now()` 约 1.8 µs，每请求两次），把三个框架拉平成同一个数——上表数字来自重写过的客户端（`rdtsc` 计时、每请求零分配、零系统调用）。131 350：那是在信封重写（916 ns → 102 ns）、响应合并成一次 `writev`、trace id 不再每请求重新分配之前测的。
- **worker 默认取满核数是错的。** 每个 worker 是独立的事件循环线程，accept 线程还要再占一核，`workers = 核数` 就是在 N 核上塞 N+1 个可运行线程。4 核机、1 000 条 keep-alive 连接实测：`WORKERS=1` 123 099、**2 → 196 569 / 190 044 / 191 828**、3 → 177 476、4 → 148 748、6 → 138 460 QPS。默认改成 `核数 - 1`（下限 1），**比旧默认高 25–30%**，热点路径一行没改——纯粹是超订。压测客户端和服务端同机时再减一核给客户端（4 核机上就是 `WORKERS=2`）；服务端独占机器时 `核数 - 1` 是安全值。（上表的扫描是在 `poll` 路径上量的；`epoll` 落地后同机 `WORKERS=2` 是 202 k、`WORKERS=3` 是 172 k。）

- **多连接吞吐**（压测器：单线程、非阻塞 `poll`、N 条 keep-alive 连接、每条连接同时只有一个在途请求——网关的真实形态，也是第一个不被压测客户端拖平的对比）：1 000 连接 `/json`，**rsboot 201 865 / axum 201 624 / actix 212 016**；200 连接 rsboot 195 652 / axum 221 382 / actix 201 002。1 000 连接上我们和 axum 平手、落后 actix 5%；200 连接上还落后 axum 11%。以前拖后腿的不是用户态——每请求 `user` 我们 2.4 µs、axum 2.6 µs——而是内核：**`sys` 每请求 9.8 µs 对 2.8 µs**，而且 200 与 1 000 连接的 QPS 一样（旧 4 worker 默认下都是 139 k），说明这是每请求固定成本，不是 `poll` 的 O(n) 扫描。

- **客户端加一条线程，排名就反过来了。** 上面所有数字都来自单线程客户端，它自己在 200 k QPS 附近就饱和：1 000 连接时三家都被按在这个天花板上，所以"和 axum 打平"里有一半是客户端的上限，不是我们的。给客户端两条线程（各 500 连接）把天花板抬高后：rsboot **221 428 / 219 306**、axum **199 690 / 199 307**、actix **263 162 / 262 465**。也就是说 actix 领先我们 **20%**，axum 在我们后面——和单线程那张表的顺序正好相反。按每请求算：我们 6.5 µs、actix 5.2 µs，其中 `user` 2.7 对 1.9 µs，`sys` 两边一样（同一窗口每 worker 5.9 s），所以 actix 赢在用户态，不在内核。同一窗口也说明了为什么调参不再有收益：`write` 占 6.3 µs 里的 4.0 µs，`read` 1.1 µs，`parse`+`build` 0.46 µs，`handle` 0.5 µs。每请求两次系统调用已经是最少的了，再往下要么批量（io_uring，或一次系统调用写多条响应），要么不动——那不是调参，是改架构。

- **20% 那个差距其实是 worker 默认值造成的。** 上面那张表是手工设了 `WORKERS=2`，为客户端留核——这个设置本身是错的。用双线程客户端在 1 000 连接下扫 worker 数，每轮 15 s：**W=1 123 827 / 125 035，W=2 227 418 / 220 739，W=3 269 438 / 266 476**。三个 worker 比两个高 **19%**，而 4 核机器上库默认就是 `核数 − 1` = 3。原因在于这个负载是**延迟敏感**而不是批量敏感：每条连接只有一个在途请求，单请求约 7 µs，把 1 000 条连接摊到 W 个 worker 上，位图和每轮就绪 fd 都跟着缩小，单请求 RTT 就降下来。只要机器不超订，worker 越多越快，而 3 个 worker + 1 个 accept 线程正好占满 4 核。

- **HTTP/1.1 流水线请求被静默丢弃了——现在还会把答案合并发出。** `BufReader` 在读第一个请求时往往已经把后面的请求一起吞进了自己的缓冲。那块缓冲 `poll` 看不见，于是答完第 1 个请求后连接就挂在那里等一个永远不来的事件：一条连接连发 4 个请求，客户端只收到 **1 个响应**，另外 3 个一直等到超时。`serve_once` 现在只要 `reader.buffer()` 非空就继续处理。接着是第二刀：排队的响应先攒进 `out_buf`，再用**一次** `write` 发出去（攒到 16 KiB 就 flush；body 超过 8 KiB 仍走 `writev` 保持零拷贝；只发一个请求的连接走的还是原来那条直写路径，字节级一致）。双线程客户端、1 000 连接、`/json`、15 s：

  | 流水线 | 之前 | 之后 |
  |---:|---:|---:|
  | 1 | 258 048 / 257 781 | 266 574 / 253 006 |
  | 4 | 374 021（4 个里丢 3 个） | **636 159 / 632 847** |
  | 16 | 516 710（16 个里丢 15 个） | **896 926 / 878 163** |

  同一窗口：actix **1 497 566**（p16）/ 765 326（p4），axum 198 732（p16，hyper 不做流水线）。也就是说客户端真流水线时 actix 还领先约 40%，但我们从**答错**变成了 887 k。

- **流水线下一个请求里，trace id 已经占 12%。** 合批把系统调用摊掉之后，单请求成本从 7.3 µs 降到 **2.55 µs**（read 0.8–1.4、parse 0.25、build 0.24、handle 0.43–1.04、write 0.23）。设 `RSBOOT_NO_TRACE=2` 后，16 深流水线从 884 k 涨到 **1 028 k**：生成 id 并插两次头的成本是 **0.3 µs/请求**。贵在两次 `Headers` 插入和两次 `Arc` 克隆，不是十六进制格式化——这是下一个值得动的地方。

- **trace id 不再分配内存，也不再经过 `Headers`。** profile 显示这一整块要 **198 ns/请求**（`build` 段 238 ns，而 `RSBOOT_NO_TRACE=2` 时只有 40 ns），成本是三处分配加一次 `Headers` 插入（十六进制先 `String`，再包 `Arc<str>`，然后 `insert_shared`）。现在 id 直接格式化进栈缓冲（`write_trace_id(&mut [u8])`），由 `fill_head` 拼进响应头——零分配、零插入。`build` 段从 238 ns 降到 **139 ns**，16 深流水线从 899 k 涨到 **972 137 / 970 340**（+8 %）。`pipeline 1` 不变，255 094 / 258 968。

- **worker 数该按请求形状定，不是按核数定。** 16 深流水线（双线程客户端、1 000 连接、`/json`）下扫 worker：W=2 **874 k**、W=3 **886 k**、W=4 **933 k**、W=6 **1 203 k**、W=8 **1 122 k**、W=12 **1 155 k**、W=16 **1 133 k**。每连接一个在途请求（`pipeline 1`）时：W=3 **256 k**、W=6 **241 k**、W=8 **223 k**。也就是说 `核数 − 1` 对浏览器、普通网关是对的，而客户端真流水线时 **1.5 × 核数** 能高 36%——三个 worker 时流水线客户端每轮有一大段时间在等，六个能把核塞满。W=6 时 `poll` 阻塞占比 9–10%，说明机器已经吃满：**1 188 338** 就是这台 4 核 VM 的上限，那个配置下 profile 是 4.3–5.4 µs/请求（争抢把单请求拖长了，但并行度换回了吞吐）。建议：默认别动，确定客户端会批量时再调 `workers`。

- **读缓冲大小：流水线下没有影响。** 1 KiB 对 8 KiB，1 000 连接两档都测：流水线 16 **952 k vs 956 k**，流水线 1 **260 k vs 260 k**。1 KiB 只装得下约 12 个请求头，16 深确实要读两次——但一次 read 摊到 16 个请求只有约 60 ns，所以从来不构成瓶颈。留了个 `RSBOOT_READ_BUF` 当诊断开关，不是收益。

- **这台 VM 的时钟是冻结的——上面那些数字全是在忙轮询下测的。** `rdtsc` 能过 20 ms 校准（2 596 刻度/µs），然后就彻底不动：2 000 万次背靠背读取返回完全相同的值。后果是静默的：`now_ns()` 变成常量，`wait_fd_until` 的截止点永远不到（读超时、空闲连接回收、协程 deadline 全部失效），worker 的 `poll` 超时被 clamp 到 0——每个 worker 都在空转而不是睡。修法是在运行期检测冻结（连着 64 次换算后的**纳秒**值相同，不是原始刻度——冻结的 TSC 仍会抖几个刻度），检测到就降级用 `Instant`；请求级的 `now_ns()` 改成每 64 次调用才真取一次时钟、其余读线程局部缓存，因为这台机器上 `Instant` 要 1.8 µs。结果：`pipeline 1` 从 **256 k 到 298 k**（+16%），`pipeline 16` 从 1 188 k 掉到 **1 045 k**——**是掉**，因为旧数字是忙轮询从客户端手里抢 CPU 抢出来的。同窗口三方：p1 rsboot **298 327** / actix 276 240 / axum 248 641；p16 actix **1 556 135** / rsboot **1 045 360** / axum 200 116。也就是说真实网关那种形状 rsboot 已经领先 actix 8%，而客户端真流水线时落后 33%。

- **流水线请求剩下那部分花在协程调度上，不在任何一段里。** `[prep]` 现在有 `serve` 段，一轮终于能对平：165 条连接、一轮 6.9 ms，其中 **pump 99.7%**、serve 0.17%、poll 等待 0.1%。每请求五段合计 **1.0 µs**（read 115、parse 225、build 86、handle 346、write 226），而按轮算出来是 **2.8 µs**——缺的 **1.8 µs** 就在 `pump` 内部：spawn、`serve_once` 的边界、`flush_out`、以及 `Request`/`Response`/`Conn` 的析构。这是下一个该装探针的地方，也是唯一还大得足以值得动的地方。

- **响应体在流水线下值 8%。** `/empty`（`Response::new(200)`，无 body 无 JSON）对 `/json`（60 B 走 `Response::json_with`）：**1 126 078 vs 1 045 360**。上一轮 A/B 说"噪声"——那是被污染的窗口；干净窗口里每请求那一次 `to_vec()` 是真金白银。p1 的账在别处：`write` 占 6.8 µs 里的 4.8 µs，其中 `flush` 单是 4.5 µs 纯系统调用时间，用户态改不动。


  一个需要知道的行为变化：服务端生成的 id 现在**只出现在响应头**。`req.request_id()` 仍返回客户端发来的那个值，但 `req.headers` 里不再有服务端生成的副本。如果某个 handler 用 `req.request_id()` 打日志、再拿它去和响应头对账，那么客户端没带 id 的请求现在会拿到 `None`。



- **同一窗口、三方都用各自默认配置：** 1 000 连接 rsboot **268 163 / 269 438**、actix **260 051 / 261 986**、axum **217 062 / 196 272**——rsboot **领先 actix 2.6%**、领先 axum 23%。200 连接：rsboot 269 566 / 271 213、actix 275 465 / 275 556、axum 200 650 / 203 006——**落后 actix 1.9%**。所以之前那句"actix 领先 20%"是手工设 worker 数造成的假象，不是哪个服务端的天性。200 连接持平，1 000 连接小胜。


- **fd 被复用后，epoll 事件会静默丢失。** 这是 `epoll` 后端带进来的回归，被短连接 A/B 抓出来。`close(2)` 会在我们背后把这个 fd 从 epoll 集合里删掉，而位图还以为"已注册"——下一条拿到同一 fd 号的连接于是**永远收不到读事件**，只能干等 500 ms 兜底超时。空闲 keep-alive 看不出来，短连接立刻暴露：20 线程 `--close`，P99 从 1.1 ms / max 2.3 ms 变成 **P99 24 ms / max 167 s**。现在 `Conn` 实现了 `Drop`，把 fd 记进一个无锁的 thread-local 队列，下一轮开头统一发 `EPOLL_CTL_DEL`；周期性全量重建保留做第二道保险。修完同一窗口：P99 **1.16 ms**、max 2.9 ms。

- **响应头改成预分配。** `Headers::new()` 一起手就留 4 格，解析出来的请求头表多留一格给 `x-request-id`。这两处原来是 0 起步，等于每请求在最热的路径上 2–3 次 `realloc`。效果：**+2.5%**（双线程客户端 221 k → 226 k），注入 trace id 的成本从 6.3% 降到 3.7%。这个拆分是用 `RSBOOT_NO_TRACE=1`（固定 id、仍插两次头）和 `=2`（完全不插）量出来的：id 生成本身几乎免费，贵的是那两次插头。

- **写次数计数器其实在把两个 worker 混在一起算。** `WRITE_CALLS` 是进程级的 `AtomicU64`，而它被除的那个请求数是线程局部的——于是每个 worker 那一行都是拿**两个 worker 的总写入**去除**自己的**采样请求数。之前那个 `wr 1.80/req` 与 `wr 0.32/req` 就是这么来的：一个真实总量被劈成两份，不是真的多了一次系统调用。改成线程局部后，两个 worker 都稳定打印 **wr 1.00/req、eagain 0.00**——每个响应正好一次 `write`，从不在背压上让出。双线程客户端实测（1 000 连接、`WORKERS=2`）：read 1.2–1.3 µs、parse 0.27、build 0.21–0.23、handle 0.55、write 4.9–5.7 µs，加压下每请求合计 7.2–8.0 µs。

- **把套接字缓冲调小：没有收益。** 默认 `SO_SNDBUF` 会自动调优，能涨到几 MB，而一个 260 字节的响应用不上那么长的队列。新加的 `RSBOOT_SNDBUF` / `RSBOOT_RCVBUF`（opt-in、仅 Linux、不设等于行为完全不变）把两头钉到 4 KiB。三轮交替：默认 228 179 / 223 861 / 221 611，4 KiB 225 005 / 223 228 / 225 172——**−0.04 %，在噪声里**。这个开关留着当诊断用，不是收益；写在这里是为了别有人再跑一遍同样的实验还指望它能涨。


- 空闲的 keep-alive 连接不再每条占 8 KiB。`BufReader::new` 会立刻预留默认缓冲，1 000 条挂着的连接实测 15.6 MB RSS；改成 1 KiB 起点 + 空闲时 `shrink_to`（只在安静满一个 `io_timeout` 之后做），同样 1 000 条落到 6.7 MB——**每条空闲连接省 9.2 KB**，同窗口压测吞吐无变化。请求体读取不受影响：剩余长度超过容量时 `read_exact` 会绕过缓冲直读。

- 请求头解析**只扫一遍**：一次字节扫描切行、顺带校验 CR/LF（孤立的 `\r`/`\n` 直接 400，那是值里做 CRLF 注入的入口）、记住冒号位置、算出 OWS 边界。token 校验查 256 项静态表，`Headers` 一笔分配装完，`Connection` 在解析时就按 token 比好，不再事后重扫一遍头、也不再整条 `to_lowercase()`。微基准：3 头请求 **346 ns → 205 ns**，真实 12 头 **1 260 ns → 680 ns**。3 头时端到端省 140 ns（总量约 11 µs），落在噪声里；它兑现的地方是浏览器/网关那种头多的流量，不是我们自己的压测客户端。

- 路由分派是**段级前缀树**，不是扫描。同在 `/api/v1/...` 下挂 200 条路由时，早先的按首段分桶会把它们塞进同一个桶，于是每个请求都扫一遍：命中最末一条静态路由要 8 947 ns、参数路由 15 576 ns。现在分派成本是 O(段数)——同样 200 条的最坏情况 218 ns / 291 ns，4 条路由的普通表 247 ns，顺带消掉三笔每请求分配。这些全是微基准；4–8 条路由时端到端看不出来，这也正是当初它没被我们的压测发现的原因。

- 响应头缓冲现在**按连接分配，而不是每请求分配**（`fill_head` 微基准：每条响应 163 ns → 109 ns）。端到端它消失在噪声里——同窗口 A/B 中位 230 200 对 232 270 QPS，波动 ±25 %——所以只为「稳态零分配」记这笔功，不当卖点。顺带把两件事钉住：`poll` 阻塞占 worker 时间 14 %，小响应本就一次 `writev` 发出，剩余差距不在这两处。
- 一条连接只占**一个 fd**，不是两个。早先 `Conn` 既存 `TcpStream`，又为 `BufReader` 存一份 `try_clone`：每连接一次 `dup(2)`、两个 fd、两次 `close`。现在写响应直接取 reader 里那个 fd。同窗口实测，accept 线程每连接成本 **6.6 µs → 6.2 µs**（该线程 −4.6 %），三轮交替 A/B 的 QPS 从 55.4 k 到 56.6 k（+1.4 %，噪声边缘）。留下的理由是那次系统调用和 fd 配额，不是这个百分比。

- 剩下的时间到底花在哪。`RSBOOT_PROFILE=1` 在这台机器上给出的每请求分解是：read 1.5–2.4 µs、parse 约 0.4 µs、build 约 0.4 µs、handle 约 0.8 µs、**write 14–18 µs**——一次 `write` 系统调用占了每个请求的约 80 %。同样 60 字节写到一对安静的 loopback 上只要 **3.1 µs**；20 客户端压测下要 14–17 µs，中间那 11 µs 是内核去唤醒同机另一个核上的客户端线程的调度账，不是这个服务端做的事。计数器是 `wr 1.00/req, eagain 0.00`：写路径每条响应恰好一次系统调用、从不因反压让出。所以 `/json` 已经贴在 IO 下沿——再抠 handler、解析器或路由，动的是 17 µs 里的个位数百分比。

- 下游调用：40 并发 × 20 ms 依赖，协程档 **655 QPS / P99 62 ms**，阻塞档 **33 QPS / P99 2 323 ms**——只差一个开关（`RSBOOT_BLOCKING_IO`），20 倍差距。

这些数字会随机器漂移。只在同一次运行内横向比较，不要跨机器比，也不要跟别人的博客比绝对值。

## 设计亮点

1. **零第三方运行时。** HTTP/1.1 解析、keep-alive 连接管理、`writev` 批量写、poll 循环、M:N 调度器全部在仓库内。依赖层级是 serde 级，不是 tokio 级。少一层活动部件，也不用把版本绑在某个异步运行时的内部实现上。

2. **handler 保持同步，却不阻塞服务。** handler 就是 `fn(&mut Request, &Context) -> Result<Response, ApiError>`。有栈协程让状态活在真实栈上，`&mut Request` 可以跨让出点持有——这是编译器生成状态机做不到的事，不然就得在生命周期上打一堆补丁。

3. **两层刻意分开。** 连接由事件循环多路复用，请求跑在协程里。协程数量对应的是**正在处理的请求**，不是打开的连接——所以 keep-alive 连接每条只花几十字节，而不是 64 KB 栈。

4. **数据库 socket 会让出。** `mysql+co://…` 让 MySQL 驱动走协程 socket，慢查询把请求挂起，而不是焊死一个 worker。钩子是进程级、模式是线程局部，所以同一进程里的两个引擎不会互相污染。

5. **下游调用也让出。** `ctx.service("name")` 自带连接池、重试、熔断；socket 读是协程感知的，一个慢依赖只拖慢一个端点，不会拖垮整台服务。

6. **一个响应体，一个错误类型。** `Api(...)` 把成功和失败包成同一形状；`ApiError` 是 handler 唯一会返回的错误类型，状态码映射由它负责。SQL 原文和内部路径进日志，绝不回给客户端。

7. **安全在启动期失败，不在运行期失败。** CORS 配置写错就起不来，而不是静默放行一切。令牌桶限流、安全响应头、连接串密码脱敏都是内置的。

8. **生命周期与优雅下线是一等公民。** 模块实现 `init / start / stop / drain` 四钩子，逆序关闭。收到 SIGTERM 先进跛鸭期（`http.drain_secs`），此时 `/ready` 返 503，让负载均衡在连接被硬断之前把流量摘走；关闭期新请求返 503，而不是连接被重置。

9. **OpenAPI 是长出来的，不是贴上去的。** `RouteDoc` 挂在路由定义上，`/openapi.json` 与 `/docs` 和 handler 共用同一个事实来源。

10. **配置分层、dev/prod 分离、支持热加载。** YAML / ini / env 三层，`app.env` 切换行为，文件监听器让你改配置不用重启。

## 快速开始

```bash
cargo run --example hello
curl -i http://127.0.0.1:8000/api/hello/rsboot
```

最小形态：

```rust
use rsboot::{ApiError, App, Config, FromRequest, Path, Response, Router};

fn main() -> rsboot::Result<()> {
    let config = Config::new()
        .set("app.env", "dev")
        .set("http.bind", "127.0.0.1:8000")
        .set("http.docs", "true");

    let mut app = App::builder()
        .config(config)
        .database("default", "sqlite:///hello.db")
        .build()?;

    let router = Router::new()
        .get("/", |_, _| Response::text("rsboot is running\n"))?
        .get("/api/hello/{name}", |req, _| -> Result<String, ApiError> {
            let Path(name) = Path::<String>::from_request(req)?;
            Ok(format!("hello, {name}"))
        })?;

    app.serve(router)
}
```

`serve` 自带信号处理：停止 accept、等 worker 收尾、逆序关模块，不需要在外面再叠一套。

## 已知限制

如实列出，因为一个藏起短板的框架比一个写明短板的框架更糟：

- SSE、WebSocket、JSON-RPC 2.0 尚未实现（规划中的 S11–S13）
- gRPC 明确不做：它要 HTTP/2，等于把 `h2` 拉进来，与「零第三方运行时依赖」冲突
- 认证只到 `Bearer` / `ApiKey` 两个提取器，没有完整的角色与权限体系
- 协程栈固定 64 KB，1 万并发约需 640 MB 栈内存
- 客户端**建连**仍是阻塞的，连接建立之后的读写才走协程
- 主路径上读请求头与请求体仍可能阻塞 worker
