# 性能实验台账

README 只放结论。这里放每一次改动的数字、每一次回退的原因，以及复现方式。**引用任何数字前先看「测量协议」**——历史上有一半的误判来自换口径。

## 测量协议（当前）

- 服务端 `WORKERS=4`（满核），客户端 **4 线程**、1 000 条 keep-alive 连接、`pipeline 16`。
- 每档 **10 轮 × 8 秒**，A/B 逐轮交替；跑两批，批间反序（AB 批、BA 批）。
- 合并 20 轮看**均值** + **胜场分布**，同时看 AB 批与 BA 批各自的方向。两批方向相反时判为噪声，不算收益。
- 噪声底：同一份代码两个二进制对比，均值差异在 **±0.35%** 以内，胜场 10:10 到 13:7 都可能出现。低于这个量级的"收益"不要当收益。

两个曾经踩过、会直接改变结论的坑：

1. **客户端线程数**。同一服务端、同样 1 000 连接 p16：客户端 2 线程 1 275 k，4 线程 1 582 k。客户端单线程会在 ~200 k 处打满自己，把三个服务端的差异全部抹平。任何跨框架对比必须写明客户端线程数。
2. **测机是否干净**。旧 4 核 VM 宿主争用严重，同一份代码吞吐从 1.46 M 掉到 0.79 M；用它做 A/B 会得出完全相反的结论。当前主测机是一台 4 核 Xeon 8255C 云主机（OpenCloudOS 9.4 / glibc 2.38），稳定在 ~1.0 M，且该机不是空机（另有 openresty、nginx、几个业务进程在跑，负载 0.00），压测全程用独立端口。

## 当前站位

同一台机器、双方都 4 worker、客户端 4 线程 p16、20 轮两批反序：

| | QPS | 对比 |
|---|---:|---|
| rsboot | 999 411 | — |
| actix-web 4 | 1 033 174 | rsboot **−3.27%**，胜场 1:19 |

AB 批 −2.77%、BA 批 −3.76%，同向。旧 VM 更早的窗口是 −4.4%(4:16) 和 −0.2%(10:10)，两台机器指向同一量级：**actix 领先 3–4%**。

## 已生效（含收益）

| 改动 | 收益 | 口径 |
|---|---|---|
| 计时探针改为编译期 feature（默认构建无探针） | **+1.64%**，14:6 | 每请求省 7 次 `OnceLock` 原子读 + 分支，实测 10–15 ns；两台机器分别 +1.62%(15:5) / +1.64%(14:6) |
| 请求行一趟扫描（同时收行尾与两个空格位置） | +0.27%，10:10 | 中性，价值是代码更短 |
| 名字字段合并扫描（取冒号 + 尾部 OWS + token 校验并成一趟） | −0.06%，13:7 | 中性，净减 33 行，补 3 个 OWS 单测 |
| `dispatch` 去掉 `req.path.clone()` | — | 少一次 `String` 复制 |

## 已否决（都测过，别再试）

| 实验 | 结果 | 根因 |
|---|---|---|
| `Hdr` 从 64 字节压到 32 字节（`Item{pos,len,tag}` + 外挂切片表） | −0.59%，9:11；AB +1.2% / BA −2.3% 方向相反 | 拆表多一次间接寻址 |
| parse 热循环用 `get_unchecked` 去边界检查 | **−1.69%**，14:6 | 分支预测本来就把边界检查吃掉了，unsafe 反而挡住优化 |
| 响应头跳过名单加首字节预筛 + 值 CRLF 改手写单趟 | −1.36%，12:8 | `str::contains('\r')` 走 memchr 向量化，手写字节循环更慢 |
| `slice()` 改 `from_utf8_unchecked` | −0.99%，12:8 | 同上，边界检查不是瓶颈 |
| 响应头 `Vec` 线程本地池化 | −0.35%，12:8 | 还给 `Headers` 加 `Drop` 会让 `Conn::serve_once` 里的借用延伸到函数末，编译不过 |
| `-C target-cpu=x86-64-v3` / `native` | 新机 +0.92%(AB −0.38% / BA +2.25%)，旧 VM +0.82%(AB −0.10% / BA +1.77%) | 两批反向 = 噪声 |
| `Headers` 内联 12 槽省一次 malloc | −8.3% | 64 字节 × 12 的 memset 比一次 malloc 贵 |
| 自研 tcache 分配器（feature `tc-alloc`） | +0.36% | 天花板 ~0.5%，默认关 |
| 全部攒进 `out_buf` 合并写（去掉每响应直写分支） | −4.3% | 客户端在途请求摊薄了 RTT，服务端基本只见 1 个请求 |
| 读侧统计探针（`note_read` + 采样） | −2.3% | 采样机制本身在热路径上 |
| 同一协程连跑多请求 / 每连接常驻 task | −12% | 破坏了按 fd 降序的服务顺序与延迟摊薄 |
| `SO_REUSEPORT` 每 worker 自己 accept | 无收益 | accept 线程稳态每 5 ms 才醒一次，不花钱 |
| 关协程（`RSBOOT_NO_CORO=1`）/ io_uring 批量化 / 调小 SNDBUF、RCVBUF | 更差或无收益 | 见 README 对应条目 |
| 读缓冲 4 KiB 作默认 | +0.8%，不显著 | 1 KiB 已能装 ~12 个请求头 |

## 剖面上看到的钱在哪

4 worker、p16、QPS ~997 k、每 5 000 请求采样一次，每请求阶段耗时（ns）：

`read 1465–3301` · `parse 262–806` · `build 137–184` · `handle 418–1250` · `write 362–1645`

合计 2 829–6 287 ns。`wr 1.00/req`、`eagain 0.00`——每响应恰好一次 `write`，从不因背压让出。

**两次 syscall 占 3.5–4 µs，约 70%**；用户态只剩约 1 µs（parse ~275 + build ~145 + handle ~555）。所以 3% 的差距 ≈ 150 ns，只可能落在 parse / build / handle 这三段。

## gdb 采样（无 perf 时的替代）

无可用的 `perf`（`perf_event_paranoid=2`），改用 40 次 `thread apply all bt 6` 打点，符号未 strip：

| 落点 | 占比 |
|---|---:|
| 写路径（`write_fd_all` + `write_response` + `fill_head`） | ~55% |
| 路由/handler（`Router` / `Node` / `service_ready`） | ~34% |
| `parse_head_with` | ~9% |

写路径一半以上是内核态时间，用户态能动的只有 45% 里的一部分。

## 结论

1. **解析器不再值得投**。三次结构性改动（名字合并、`Hdr` 压缩、去边界检查）全部落在噪声底内或微负。275 ns 的耗时不在"扫几趟"，在每请求的固定动作：头条目构造与写入、`Vec` 清空与容量检查、偏移切片入库、收尾校验。
2. **要把 3% 追下去，先测量再动手**。下一步该在 `route.rs` 的 `dispatch`/`finalize` 与 handler 返回处加 1/64 采样（`profile` 已有采样开关，开销可忽略），把 handle 的 555 ns 拆成"路由匹配 / 上下文 / 用户 handler / 响应构造"四段。在那之前任何"应该会快"的改动都只是又一轮 ±0.5%。

## 复现

本地两批反序：

```sh
./ab5.sh <A-binary> <B-binary> AB && ./ab5.sh <A-binary> <B-binary> BA
```

逐轮取数 `| tail -1 | awk '{print $(NF-1)}'`，按"AB 批奇数位=A、BA 批奇数位=B"分派，算均值/胜场/分批 delta。

带剖面要单独编一份带探针的二进制（`--features prof`），`RSBOOT_PROFILE=1` 启动；**带探针和不带探针的二进制不能混着比**（探针本身慢 1.6%）。
